# Restore schema manifest evidence

## Scope

`lib/db/restoreSchemaManifest.ts` is a read-only catalog gate for replacement
restore preparation. It does not open a database, execute candidate SQL, run
bootstrap, migrate data, or write live data. Its connection surface is one
generic `getAllSync(sql)` method so the production Expo `SQLiteDatabase` and the
Node host adapter can both call it.

The compiled allowlist version is `replacement-restore-schema-v1`. That ID
versions the whole supported allowlist; it is not the name of one physical
layout.

Validation reads:

- `sqlite_schema` for every catalog object and its stored SQL;
- `PRAGMA table_xinfo` for column order, affinity, defaults, nullability,
  primary-key position, and hidden/generated state;
- `PRAGMA foreign_key_list` for foreign-key targets and actions;
- `PRAGMA index_list` and `PRAGMA index_xinfo` for declared and implicit index
  uniqueness, origin, partial state, key order, collation, and direction.

Schema SQL is token-normalized only outside quoted strings and identifiers.
Whitespace and keyword case are ignored, while quoted default/check values are
kept byte-for-byte. Tests prove that a changed quoted default is rejected.
Unknown tables, columns, column orders, constraints, foreign keys, indexes,
triggers, and views fail with `RestoreSchemaValidationError` and stable code
`unsupported_schema`.

SQLite-owned objects are handled explicitly. The manifest lists the exact
`sqlite_autoindex_*` objects generated by evidenced `UNIQUE` constraints. It
does not ignore names beginning with `sqlite_`; an unexpected retained
`sqlite_sequence` table is rejected in the regression suite.

## Evidenced profiles

The source phase always requires `exercises`, `workouts`,
`workout_exercises`, and `sets`. The other 11 app tables may be absent and are
reported in `missingOptionalTables`. This is an explicit preparation policy,
not a claim that every absence combination has been observed in a historical
database: the accepted MVP-006A proof enumerates those same 11 names in its
`OPTIONAL_TABLES` contract, and the ADR makes only the four history tables
mandatory before migration. A synthetic policy test drops all 11, runs the real
bootstrap, and proves they are recreated empty. Per-table omission tests cover
all five production exercise fixtures; when a populated parent table is
omitted, its optional descendants are omitted as well so the test input remains
referentially valid. The current phase requires all 15 ADR tables and no
obsolete objects.

The allowlist contains these correlated profiles:

1. The populated MVP-003B production fixture baseline from pinned schema
   `5892c323`, with the exact pre-migration index states used by the five
   production exercise fixtures. The exercise definitions are tied to their
   evidenced explicit-index state instead of being combined arbitrarily.
2. Current bootstrap output over that baseline. It permits exactly the five
   exercise table outputs named by production `EXERCISE_SCHEMA_SHAPES`:
   `current-canonical`, `uid-era-fresh-then-variations`,
   `pre-uid-direct-upgrade`, `pre-uid-sequential-upgrade`, and
   `0923b8d-fresh-direct-upgrade`. All other tables and all indexes remain tied
   to the same fixture baseline.
3. The exact fresh-install output of
   `git show e9ee8ed7:lib/db/connection.ts`. It includes the five exact obsolete
   program tables that normal bootstrap later removes. At this checkpoint
   `workout_exercises` ends at `current_reps`; the later `completed_at` and
   `performed_at` columns do not exist. Its declared indexes likewise exclude
   the later `idx_sets_workout_exercise_id` and workout-exercise timestamp
   indexes. A regression asserts this exact column and declared-index boundary.
   This is a complete historical DDL fixture, rather than current tables
   populated with null UIDs. It specifically evidences the absence of the later
   `user_checkins` and PSL tables; other optional omissions are authorized by
   the preparation policy above rather than presented as historical
   observations.
4. The current family produced by running today's real `initializeDatabase()`
   over that exact `e9ee8ed7` fixture. Its appended core columns and fifth
   exercise order remain correlated. Settings, PR events, and media each have
   one additional canonical form only because bootstrap creates that form when
   the corresponding policy-optional e9 table is absent. Tests exercise all
   eight combinations of those three independent omissions. No unrelated table
   shapes are combined into this family.

Every database accepted by the current phase is also accepted as a future
source. Tests validate `source -> initializeDatabase() -> current -> source` for
all five production exercise fixtures and the exact e9 fixture. They also run a
second bootstrap after each of the 11 policy-optional tables is omitted from an
e9-migrated database. The e9 historical fixture separately covers each optional
table it physically contains. These are bootstrap-output and policy tests; they
do not relabel synthetic omissions as observed historical catalogs.

The `a97acf7`, `39cc234`, `3223ce9`, `76c70e2`, `0f25ee6`, and MVP-003B
references in the production exercise fixture names establish exercise-table
orders only. They are not treated as evidence for arbitrary full-catalog
mixtures.

## Retained populated Android evidence

On 2026-09-22 the retained host snapshot at
`.codex-artifacts/mvp-notes-native-20260922/before-inspection/LiftingLog.db`
was opened with Node SQLite's read-only option. Only catalog queries were run;
no training rows were printed or copied. The exact snapshot validated for both
`phase: "source"` and `phase: "current"`, returning all 15 app tables, no
missing optional tables, and manifest ID `replacement-restore-schema-v1`.

## Deliberate compatibility limits

Fresh databases predating `e9ee8ed7` created `best_lifts`. Current bootstrap
does not remove that table, and the ADR authorizes normal removal only for
`planned_workouts`, `progressions`, `program_exercises`, `program_days`, and
`programs`. A database retaining `best_lifts` therefore fails closed. No older
full-catalog profile is promised without a reviewed migration/removal rule and
an actual physical catalog fixture.

Intermediate historical full catalogs are also not inferred from individual
column migrations. They remain unsupported until a retained database or exact
historical startup output supplies the complete table and index evidence.

The host tests use Node 22's experimental `node:sqlite` binding. SQLite catalog
and PRAGMA semantics are the same contract used by Expo, but the tests do not
prove Android/iOS SQLite build parity, validation-only Expo open behavior, or
that an Expo read-only session leaves the database-file digest unchanged.
Those remain native preparation gates in the replacement-restore ADR. No SQL
parser dependency is installed in this repository; the implementation uses
SQLite's own catalog and PRAGMA introspection rather than executing untrusted
DDL or maintaining a permissive DDL parser.
